# 配置管理设计指南

本文档说明 `infrastructure/config/` 的配置组织方式，以及为什么选择 YAML 而非其他配置形式。

## 目录内容

| 文件                 | 说明                                       |
| -------------------- | ------------------------------------------ |
| `settings.dev.yaml`  | 开发环境配置，可安全提交到仓库             |
| `settings.prod.yaml` | 生产环境配置骨架，敏感项必须用环境变量注入 |



## 为什么采用 YAML ？



#### 对比硬编码常量/配置类

YAML 将配置与代码分离，同一套代码加载不同环境的 YAML 文件即可切换，改配置不需要动代码。

- **配置与代码耦合**：改配置必须改代码、重新部署，无法做到"部署时调整"；
- **环境无法差异化**：开发、测试、生产共用一份值，无法按环境切换；
- **无法演进**：配置项增加时需反复改动代码结构。





#### 对比环境变量（env）

环境变量比较适合**注入密钥类敏感项**（密码、token、私钥），但不适合承载全部配置：

- **可读性差**：随着业务扩展， 配置项多了以后，环境变量无法结构化组织；
- **不支持嵌套**：JWT、数据库、邮件等分组配置难以表达层级关系；
- **无类型与校验**：字符串到 int/bool 的转换需手工处理。
